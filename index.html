How it works

Five fixed steps. The same alerts always give the same list.

Why this order: an attack is usually a short run of unusual alerts on a few connected machines. Routine activity, such as mail logins, antivirus updates or package downloads, fires all day on many machines. Rarity weights the first up and the second down. Linking by shared host or address keeps the steps of one attack together.

Measured, with the failures

The data: the public AIT Alert Data Set (Landauer, Skopik and Wurzenberger, CC BY 4.0). It holds Wazuh and Suricata alerts from eight runs of a multi-step attack (scans, web attacks, cracking, a reverse shell, privilege escalation, DNS exfiltration) inside days of normal activity. An alert counts as attack-time if it falls inside one of the data set's labelled attack windows.

The method was fixed first. It was developed on one scenario (russellmitchell, the smallest). The kernel and the metrics were then committed (5cc52e6), and only after that were the seven others run, once (b996c20). The comparison is a severity-sorted queue, one group per rule ranked by its highest level, which is what many analysts start from.

Where it wins

In every scenario the first group is an attack, against rank 2 to 4 for the severity queue. The top ten groups hold 81–100% of all attack-time alerts, against 7–10%. It finds more of the attack's phases in the top ten in all eight scenarios.

Where it loses

"Top 10 that are attack" is lower (10–20%, against 20–50%). That is the cost of its design. One attack becomes one incident, so the other top slots go to the next most unusual activity, which is usually benign. The severity queue spreads one attack across several rule groups and so scores higher on this measure.

What it misses

DNS exfiltration is missed in all eight scenarios. The data set's paper says that while it runs, an alert flags it in only two of them: in harrison and santos, Suricata marks the attacker's .biz domain. Version 1 reads those alerts and still ranks them below its top 10. In the other six, the traces are AMiner alerts raised after the exfiltration stops, outside the labelled attack time. The first network scans leave very few alerts and are also missed. Some scenarios also miss the web shell, the reverse shell or the cracking.

Caveat: the labels are by time. A routine event that happens inside an attack window counts as attack-time, so the attack-time measures can flatter both methods equally. One change was made after the test run. On an export covering less than 24 hours, no rule is set aside as routine any more, because over a few hours of an attack every rule would qualify. Every scenario covers several days, so re-running all eight with the change gives identical results, which is recorded in commit 03a3111. To re-run everything yourself: download ait_ads.zip and labels.csv from Zenodo, then run node tools/measure.mjs ait_ads.zip labels.csv russellmitchell fox harrison santos shaw wardbeck wheeler wilson.

The blueprint

triage.mjs

The whole method in one dependency-free file: normalise, bursts, routine noise, incidents, score. Its tests are themselves tested: a mutation gate breaks the code on purpose, one operator at a time, and every break must be caught. This page runs it byte for byte.

bin/triage.mjs

The command line: JSON lines (streamed, so large exports are fine), a JSON array, or CSV. It prints the ranked list, or JSON with --json. Options: --burst-gap, --incident-gap, --background-share.

tools/measure.mjs and results/

The measurement exactly as run, and its output for all eight scenarios. Anyone can re-run it and compare.

Limits, answered straight

  • It ranks the alerts your tools raise. It cannot find an attack that raised no alert.
  • It missed DNS exfiltration in every test, and early network scans, as shown above. Do not rely on it alone for those.
  • Benign but unusual activity ranks high too, such as an administrator's rare login. Ranking is not a verdict: the list says what to look at first.
  • The measure is one public data set of one network and one attack chain, run eight times with variations. Your network is different, so run it beside your current process before you rely on it.
  • Large exports belong on the command line. The browser holds the whole file in memory. The command line streams it: in our run it triaged the largest scenario, 625,303 alerts from a 674 MB file, in 17 seconds on one desktop machine.
  • It is a first pass, not a replacement. Take the top groups into your SIEM or case tool and investigate them there as usual. Keep your existing alerting for the things it misses.
  • Version 1 does not read AMiner or other anomaly-detector formats unless they are flattened to CSV first.
